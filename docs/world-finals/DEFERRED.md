# Deferred — world finals

Every inconsistency, rough edge and shortcut found while building Continuity 2.0 that was
**not** resolved at the time. Nothing here is a surprise; everything here is a decision.

Same format and the same rules as [`docs/DEFERRED.md`](../DEFERRED.md), which covers the
preliminary build and is still live. This file is scoped to the finals work so the two do not
have to be read together. Items are removed when fixed.

**Severity:** 🔴 would be wrong on stage · 🟡 wrong but survivable · ⚪ cosmetic or future ·
🔵 researched and deferred by decision — the direction is settled, a prerequisite is not

|---|---|---|

What remains is that the cache is in process memory and empty after a restart. | `api/boards.py` |

| 🔴 | **A review holds one spinner for about twenty-five seconds before it says anything about the board.** Measured on screen, twice: the candidate list lands at ~10 s and the first line about this product line at ~35 s, with the run ending at ~60 s. The gap is `board_for_line` resolving the line's three parts against the distributor, one at a time, after the catalogue search has already finished. | ⚪ | **`BoardConsequence` re-places the part on every toggle to BOARD**, because `auto` fires whenever `check` changes identity and nothing caches the result. A KiCad run is several seconds and the answer for a given (line, retiring, candidate) does not change. | `board/BoardConsequence.tsx` |
| 🟡 | `backend/.env` still points `DATABASE_URL` at production, so a local run started without an override writes real rows. Every browser check this session used `DATABASE_URL=postgresql:///<scratch>` and `CONTINUITY_FIXTURE_DIR=<scratch>`, which works and is the standard to write down — the gap is that it is a habit rather than a default. | `backend/.env` |
| 🟡 | **A candidate can still be excluded for ambiguity where the answer is knowable.** The BOM disambiguates a *fitted* part, but a candidate somebody names has no such record — so `TLV1117LV33DCYR`, which PARTS.md already resolves to TI's listing, is skipped rather than checked. The screen says so plainly, which is the honest floor; letting the caller name a manufacturer would be the fix. | `api/matrix.py` · `api/notices.py` |
| 🟡 | **The seed is the only writer of verified part facts.** `tools/seed_world.py` marks the PARTS.md readings as verified, so the datasheet-outranks-listing rule now fires — but only inside the demo company. A real account sourcing a part live still gets the distributor's parametric table for every engineering figure, because nothing verifies a reading at runtime. The θJA extractor could mark its own findings; it does not yet. | `parts/normalize.py` |
| 🟡 | **The AML gate makes every unseeded organisation's boards fail once a list exists.** Turning on an AML reports every part not on it, which is correct — and means a company must qualify its whole existing BOM before the gate is usable. The seed does this by deriving the list from what ships; a real company has no such step and no screen to do it on. | `api/lines.py` |
| ⚪ | Two accounts share one password in the seed, and it is in the repository. Fine for a demo world in a scratch database, and it must never be run against anything else — the script takes an explicit database URL and has no default, which is the only guard. | `tools/seed_world.py` |
| 🟡 | **A successful precedent is never written.** `store.worked_anywhere` reads them and the review only records *rejections*, so "a part approved on line A surfaces when line B hits the same signature" — half of item 15a's test — does not happen yet. Recording one needs the moment a substitution is **accepted**, not merely proposed, which is the approval flow. The reviewer also still reads `precedents_for_user` off `findings` rather than this table. | `api/notices.py` · `graph/nodes.py` |
| 🟡 | **The AML and AVL can only be edited through the store.** `keep_lists`, `qualify_part` and `approve_vendor` have no endpoint and no screen, so a company cannot state its own policy without a Python shell. The gates read the lists correctly; nothing writes them but tests and the seed. | `api/lines.py` · item 16 |
| 🟡 | **Approvals are recorded and never shown.** `approvals_for_thread` exists and no view reads it, so a decision with an author, a timestamp and a rationale is invisible to the next person to open the run. An audit trail nobody can see is a database table. | `routes/design.tsx` |
| 🟡 | **A notice can only be reviewed when the retired part sits at the same refdes on every affected line.** The slot is looked up per line from its own BOM, but `evaluate_matrix` takes one slot for the whole grid, so U1 on one board and U7 on another is a 409 telling the caller to name one. Real boards disagree about refdes far more often than they agree. | `api/notices.py` · `matrix.py` |
| ⚪ | `annual_volume` is a parameter of the review rather than a property of the product line, so the recurring-cost figure has to be supplied on every call and cannot be wrong in only one place. It belongs on the operating profile beside the ambient. | `profile.py` |
| ⚪ | **The outbound approval request does not exist.** A gate records the decision somebody made and never asks anybody to make it. Separate from the mail transport being deferred: the *request* is missing, not just its delivery. | `api/app.py` · item 14 |
| 🟡 | **A question shows no sign of whose it is.** `question.roles` travels on the wire and the client type declares it, but no screen reads it — so someone in the wrong department sees the question, sees an input, answers, and is refused at `/resume` with a 403. The refusal is correct and arrives far too late; the field exists precisely so the screen can say "this is engineering's to answer" before they type. | `ChatPanel.tsx` · item 13 |
| 🟡 | **The matrix cannot be built from stored data alone without a hand-written profile.** `board_from` needs rail `source` and `members`, and nothing writes them yet — the seeding in this session's verification was done by hand against the API. Item 16 is the producer. Until then the screen works only for a line somebody has described in full. | `profile.py` · item 16 |
| ⚪ | The matrix's `ambiguous` banner — one MPN listed by two manufacturers — is not browser-verified. The endpoint path is tested both as a unit and through HTTP; only the rendering is unseen. | `routes/matrix.tsx` |
| 🟡 | The θJA extractor declines on row-per-package thermal tables. onsemi's NCP1117 lists SOT-223 and DPAK as separate *rows* under section headings rather than as columns, and linearisation splits each label from its value — so there is nothing to bind against and it correctly refuses. Verified live: ST and TI extract cleanly, onsemi does not. The demo fixture states that θJA by hand, so no cell depends on it. | `parts/datasheet.py` |
| ⚪ | **Item 6, `power_dissipation_max`, is not built.** Nothing states the quantity it checks: every distributor "power" field is a different measurement, and AMS1117 and NCP1117 both say *"Internally Limited"* while TLV1117LV says *"See Thermal Information"*. For a linear regulator the dissipation limit is the thermal one. The rule's real subject is passives — a 0603 resistor's 100 mW rating is a genuine spec — so revisit when a board carries resistors. | `engine/rules.py` |
| ⚪ | **`footprint_compatibility` compares land patterns, not pin functions.** A candidate with the same footprint and a different pinout passes. Pin names reach the system only for bus masters and only to count GPIOs, so `PartSpec` keeps the count and not the names — comparing pinouts means a distributor call for every part on every board. The land pattern answers the decisive question; the pin map is unbuilt rather than half-done. | `engine/rules.py` · `parts/normalize.py` |
| ⚪ | **`p_dis_min` and `approved_only` are absent from `CONSTRAINT_FIELDS`,** deliberately. Neither has a consumer — item 6 was not built and the AML/AVL layer arrives at item 13 — and a key the model may emit that nothing reads is accepted, ignored, and looks like it worked. That is how `vout` sat in the vocabulary being silently dropped. Add each one *with* its consumer. | `reviewer.py` |
| ⚪ | The θJA package table is knowingly optimistic for SOT-223 — 62 °C/W against a 66–136 spread TI measured. Left alone by decision: it is a fallback so a part with no published figure does not halt a run, no cell in the demo depends on it, and no single number is defensible when the board's copper is unstated. | `engine/packages.py` |
| ⚪ | Most rows of that table have never been checked against a datasheet. Seven have; the module docstring names which. | `engine/packages.py` |
| ⚪ | `QFN-32-EP(5x5)` and its siblings resolve to no θJA at all. The exposed-pad guard refuses to match `QFN32`, whose values already assume a thermal pad, so QFN regulators go thermally unchecked. | `engine/packages.py` |
| ⚪ | The conflict drawer's `FAILED · ACCEPTED` label is not browser-verified. The drawer only opens on an *open* conflict, and a waived one is by definition closed, so no restored run could exercise it. Typechecked and reasoned through; the sibling path in `ChatPanel` was verified live. | `ConflictPanel.tsx` |
| ⚪ | Codex cannot run the full test suite — its sandbox is denied the PostgreSQL socket. Every delegated task has reported a partial count, and twice the full run found failures the partial did not. Every agent result needs the suite run again by hand. | tooling |
| ⚪ | **A profile's rail statements are still not applied to a *design* run**, and that stays deliberate: a design run's rail ids come from the planner, so a stored `3v3` meeting a planned `3V3` would raise mid-run and kill the board rather than correct it. Item 12 resolved the case that mattered — `profile.board_from` builds a board from the line's own BOM, where the rail ids and the profile come from one place. | `graph/nodes.py` |
| 🟡 | **The offline safety net does not cover reading a notice.** `CONTINUITY_FIXTURES=1` replays every distributor call and never touches the network, and part normalisation comes out of `backend/cache/`, so the whole review path runs on a dead connection. The notice reader calls the model directly with no recorded path, so the one step that must work first is the one step that needs the venue's wifi. Receiving the notice while online stores it and everything after replays, which is the workaround rather than the fix. | `notices.py` · `parts/fixtures.py` |
| 🟡 | **A deployed instance has no KiCad, so the board section is unavailable there.** The capability is configured with `CONTINUITY_KICAD`, and locally that is the pinned container; Render would need either an image carrying KiCad or a service beside the app to run it. Every route degrades honestly — the project is still stored, and the screen says the instance has no KiCad rather than guessing — but the demonstration's board views only exist where one is configured. | `kicad/runner.py` · deployment |
| 🟡 | **LD1117S33TR has no pin functions on file, so it gets no board consequence.** ST publishes the pin connections as a figure and a figure is not extractable text, so the part is deliberately absent from `kicad/catalogue.py` and the screen says why. Reading a pinout out of a drawing is a different capability from reading a table. | `kicad/catalogue.py` |
| ⚪ | **A retired part at more than one position on a board is refused rather than substituted at each.** The consequence names the reference designators it found and stops, because substituting several positions at once means several swaps in one file and a report that has to say which finding belongs to which. | `api/boards.py` |
| ⚪ | **The board consequence is computed on demand and never stored.** It is not part of the change request document, so the person who reads the request tomorrow sees the proposal and the cost without the layout consequence unless they press the button again. It belongs in the document beside the evidence. | `change.py` · `api/boards.py` |
| ⚪ | **The cheap-part-costs-a-respin beat is researched and not in the demo.** `ME6211C33M5G-N` is in the pinout catalogue and the KiCad tests use it, but it is not a sourced candidate: its datasheet gives 6.5 V absolute maximum input and 600 mA, which rules it out on the 12 V cabinet controller and leaves it viable and cheaper on the sensor node — where the board says it costs a layout revision. Adding it as a real part needs PARTS.md readings and a live listing, which is a flow decision rather than architecture. | `tools/eol_differential.py` · PARTS.md |
| 🟡 | **The NOT CHECKED disclosure does not survive reopening a notice.** A review that skipped a candidate says so on screen, and the skip list lives only in component state — so a person coming back to the stored change requests sees "no viable part" with no sign that one of the named candidates was excluded before it was evaluated. That is the exact omission the panel was added to prevent, restored by a page reload. It belongs on the stored review beside the requests. | `api/notices.py` · `routes/notices.tsx` |
| ⚪ | **Two notices about the same part are indistinguishable in the list.** Every entry is labelled with its MPN alone, so the full notice and the preliminary one both read `AMS1117-3.3` and the only way to tell them apart is to open each. The received date is stored and the reference number is in the document; neither reaches the list. | `routes/notices.tsx` |
| 🔵 | **Outbound mail is still deferred; inbound is being built as Phase 5.** Inbound reads a mailbox over IMAP, which needs an account and an app password and no public URL. Outbound still needs SMTP or a transactional API key with a verified sender domain, and stays deferred. Neither is hard and the code is transport-agnostic — a poller is a loop around `notices.read`, and the inbound webhook of any provider posts the same body `POST /notices` already accepts, so inbound is close to zero new code once an account exists. **The demo does not depend on it:** the POST path is verified live, with a real PDF, through the live model. What is genuinely missing is the *outbound* approval request — a gate currently records the decision and does not ask anybody for it. | `api/notices.py` · item 14 |
| 🔵 | ~~The operating profile is not persisted.~~ Ambient, copper and rail load reach the engine but live only in a fixture; storing them against a product line is item 10, which is where product lines first exist. **Resolved by item 10b, 7 Sep** — see the rail caveat above. | `api/store.py` |

## The first flow pass, 8 Sep

Sparsh ran the app end to end for the first time since the reframe. Every finding below is
one symptom of a single mistake: **2.0 was built as endpoints and three new screens hung
beside the 1.0 shell, and the old centre of gravity was left in place — a product line is
still "a design run that has not happened yet".** These are being fixed now, as Phase 5 in
[BUILD.md](BUILD.md), rather than carried.
